# Reproduction — EXP-KV-Q4-STORAGE-10A

## What's known

- **Base commit**: `a6d5377c852cc1eeb88d224b25726f74c515a405`
  (`kadireren7/membrane`, "chore: prepare MEMBRANE v0.3.0-rc1").
- **Prototype patch**: `../patches/phase10a-q4-kv-storage-prototype.patch`
  applies cleanly on top of that exact commit (touches
  `tools/membrane-run/{compat_check,main,product_cli}.{c,h,cpp}`,
  `tools/membrane-llama-runtime/{decode_loop.cpp,kv_store_telemetry.h}`,
  `scripts/verify-results.py`).
- **Models used**: SmolLM2-135M-Instruct and SmolLM2-360M-Instruct
  (referenced by name/architecture in the result artifacts; GGUF files
  are not bundled here — obtain them from their original source, e.g.
  HuggingFace `HuggingFaceTB/SmolLM2-135M-Instruct` /
  `HuggingFaceTB/SmolLM2-360M-Instruct`, converted to GGUF).
- **Hardware sensitivity**: the Vulkan/GPU-memory-pressure results
  (`results/canonical/gpu_memory_pressure_360m.json`,
  `results/canonical/performance_repetition_135m_vulkan.json`) were measured on
  an NVIDIA GTX 1650 (4096 MiB VRAM) — absolute VRAM/context numbers on
  other GPUs will differ; the relative Q4-vs-Q8-vs-native pattern is
  the more portable finding.
- **llama.cpp pin**: this experiment predates the Phase 12B
  `kv-type-override`/`kv-device-override` patches — it used llama.cpp's
  KV storage type field directly (`type_k`/`type_v`), no llama.cpp
  source patch was required for this experiment specifically. Check
  `kadireren7/membrane`'s `third_party/llama.cpp` submodule pin at
  commit `a6d5377` for the exact pinned llama.cpp commit.

## What's NOT preserved / unknown

- The exact shell commands used to invoke each benchmark run are not
  separately committed as a script in this experiment — the CLI surface
  used is the product `membrane-run --kv <mode>` binary built from the
  base commit + the prototype patch, invoked with the model/context
  values visible in each result artifact's own fields (`n_ctx`, model
  filename, etc.), but there is no single `run.sh` this phase committed.
- Raw model output text/logits used to compute the quality-ladder
  numbers are not preserved beyond what's summarized in
  `results/canonical/quality_ladder.json` and `results/canonical/q4-kv-validation.json` —
  a fresh run would need to be executed to regenerate the raw numbers,
  and might show minor run-to-run variance on top of the real signal
  described above.

## Expected outputs if reproduced

Re-running the quality ladder (Section 11 methodology, described in
`results/canonical/quality_ladder.json`) against the same two models should
reproduce the qualitative finding (Q4 meaningfully worse than Q8 on
rel-L2/NLL/top-1) even if exact percentages vary slightly run-to-run.
The storage/memory numbers (`results/canonical/storage_theoretical_vs_observed.json`)
are derived from ggml's fixed block-format arithmetic, not measurement
noise, and should reproduce exactly on any host given the same context
sizes and models.

## Reproducibility classification

**PARTIALLY_REPRODUCIBLE** — base commit, prototype patch, models
(by name), and methodology are all preserved and sufficient to re-run
the experiment and reproduce its qualitative finding; the raw per-token
logit dumps used to compute the original quality-ladder summary numbers
are not separately committed (only the summary numbers are), so exact
original percentages cannot be regenerated byte-for-byte, only re-derived
fresh.
