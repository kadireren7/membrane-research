# Hardware validation risk register

Real, disclosed risks to `docs/phase8-hardware-validation-plan.md`.
Each entry: probability, impact, mitigation, and what evidence would be
needed to close it out (i.e. move it from "risk" to "resolved fact").

| Risk | Probability | Impact | Mitigation | Evidence needed to close |
|---|---|---|---|---|
| **RTL divider resource use** — `membrane_fp_divider`'s ~73,600 LUT-class cells (real, yosys/ECP5-measured) is by far the largest single module, and `q8_scale`/`q4_scale` each instantiate two of them | High (already measured, not speculative) | Limits pipeline-replica count and raises area/cost per instance | Accept the cost for a first bring-up (single instance); consider a shared/time-multiplexed divider across Q8/Q4 paths if replica count needs to scale later | A real vendor-tool utilization report (Level A) confirming the ECP5 numbers' relative sizing holds (even if absolute counts differ) on a real Xilinx/Altera target |
| **Timing closure** — the divider's un-pipelined ~65-bit combinational divide is unlikely to close timing at any realistic clock as a single cycle | High | Blocks all of Level B/C until resolved | Re-pipeline into a genuine multi-cycle divider (restoring/SRT/iterative) if the first P&R attempt fails to close timing — planned as expected work, not a contingency | A real place-and-route timing report (Level A) |
| **PCIe setup overhead** — real host/driver/BAR-mapping configuration is a common source of "it doesn't work" that has nothing to do with the RTL itself | Medium | Wastes bring-up time misattributing a config issue to a design bug | Run loopback DMA (`hardware/experiment-protocol.md` step 5) with zero MEMBRANE logic in the path first, specifically to isolate this class of problem before introducing the core as a variable | A passing loopback-DMA log before any MEMBRANE-specific test is attempted |
| **DMA batching** — the core's native 512-bit single-beat-per-transaction framing may not match a real DMA engine's preferred burst/descriptor granularity | Medium | Could cap real throughput far below what the core's own 1 block/cycle rate would suggest | `hardware/vendor-wrapper/`'s adapter assumes single-beat transactions explicitly (documented TODO); a real integration may need multi-beat framing, added deliberately rather than discovered as a silent bug | Batch-size scaling results (`hardware/experiment-protocol.md` step 10) |
| **Board availability** — no FPGA board exists in this project's own environment; the entire Level B/C plan depends on external access | High (this is the reason this outreach package exists) | Blocks all real-hardware validation indefinitely without it | This outreach package itself (email templates, lab package, technical brief) | Confirmed hardware access from a collaborating lab |
| **CXL hardware availability** — real CXL Type-3 devices and emulation platforms are rare and often restricted to specific vendor partner programs | High — likely the single hardest risk to close in this entire plan | Level C may not be achievable in any near-term timeframe | Scope Level C as strictly optional/best-effort in all outreach material (already done — see `outreach/membrane-technical-brief.md` §9's "if a CXL platform is available" framing) | Confirmed CXL platform access from a collaborating lab or vendor program |
| **Vendor lock-in** — Vivado-targeted RTL/constraints may not port cleanly to Quartus (or vice versa) without real rework | Medium | Could require duplicating Level A effort per toolchain | `hardware/vendor-wrapper/` is written in plain, tool-agnostic SystemVerilog specifically to minimize this; constraints/timing scripts are inherently tool-specific and would need separate authoring per path | A successful Level A run on a second, different toolchain after the first |
| **Model scale** — this project's simulation/quality results are at 135M/360M model scale; hardware validation of the FPGA datapath itself is model-scale-independent (it operates on fixed-size blocks, not whole tensors), but any claim connecting hardware results back to "helps LLM serving" inherits this limitation | Medium | Risk of overclaiming relevance of a hardware pass/fail result to production-scale serving | Keep hardware-validation claims scoped to the datapath itself (bit-exactness, throughput, timing) — never imply a hardware pass validates the 135M/360M-scale software results at production model scale | N/A — a scope discipline, not something a single experiment resolves |
| **Simulation-to-hardware mismatch** — this project's Verilator cosimulation and yosys elaboration checks are real but do not model every real-hardware effect (real clock jitter, real signal integrity at 512-bit bus widths, real DRAM/BRAM timing) | Medium-High | A design that cosimulates perfectly can still fail on real silicon for reasons the simulation never modeled | Post-route simulation (Level A) and real known-vector/parity testing (Level B) are specifically the steps that would catch this — cosimulation alone is explicitly not treated as sufficient (`outreach/hardware-claim-gates.md` Gate 0 vs. Gate 3/4) | A passing Level B known-vector + 100K-parity result |
| **Tool licensing** — Vivado/Quartus (especially higher-tier editions needed for larger devices like the U250/U280) may require paid licenses a lab or this project doesn't have | Medium | Could block Level A entirely for a specific target device | Prefer whatever toolchain/device a collaborating lab already has licensed, per `outreach/target-selection.md`'s selection criteria, rather than insisting on the original U250 target | Confirmed toolchain access (any supported device) from a collaborating lab |
